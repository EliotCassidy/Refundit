# Refundit: Claude Code instructions

Refundit is a mobile-first web app. A user photographs a supermarket receipt, picks the products that had a **real** problem, and an H Company computer-use agent files the complaint on each brand's customer-service contact form. Brand replies come back to a dedicated inbound address per claim and update the claim's status.

Hackathon project: 2 devs, 1 weekend. **Working end-to-end demo > completeness.**

## Current state (keep short; update it when it changes)
- **Receipt → product (Dev 1, done):** `POST /api/receipts` parses the photo with the H model (~5–20 s). `POST /api/receipts/:id/identify` handles one item per call (~1–8 s, one short LLM call, no Linkup): Open Food Facts / Open Beauty Facts candidates + products seen at the same price in the same chain (Open Prices), ranked against the receipt label, format and price. If nothing scores well, ONE Linkup call per item (`LINKUP_PRODUCTS=true`, cached, never retried) finds the real name on the web, then OFF again; products Linkup names get +15 in the ranking (never auto-validated), and an EAN written in a web source is kept even when OFF doesn't have it. **Photos:** when no Open Facts base has a photo for the top product, ONE Linkup image search per EAN (`webImage`, `includeImages` + `searchResults`, cached, never retried, the image must name the brand; on by default with a Linkup key, `LINKUP_IMAGES=false` turns it off); the receipt page backfills it once for receipts scanned before. The user can also type/scan the barcode or type the product name (`/identify` with `ean` / `query`), or as a last resort type the product by hand (`/confirm` with `manual`). When the 1st candidate is ≥ 90% sure on our eval (`confident`), the page validates it directly; it shows only 3 proposals otherwise. Measured with `npm run eval:identify`: right EAN 1st / in the top 5 for 33% / 51% of known prices without Linkup, 40% / 59% with Linkup (37 calls, ~$0.20; `-- --linkup-cached` replays the paid answers for free, `--details` explains each weak line); auto-validations 5/5 right. `POST /api/receipts/:id/confirm` takes an `ean` that must be one of the proposed candidates, or `null` ("je ne trouve pas mon produit" → `not_found`). **Known labels are instant** (`knownCandidates`, same order in `/identify` and the receipt page): 1) products chosen by hand for this label at this chain (`product_matches`; automatic validations never write there), 2) the last full result for this label (`lookup_cache`). `full: true` = search again. A validated (green) product can always be changed; the correction counts (the replaced product loses its manual confirmation, the cached result stops being auto-validated). **Brand guard:** a candidate of another brand than the registry brand read in the label (e.g. Coca-Cola on "NOTCOCA…") is never auto-validated. In production, lookups are cached in Supabase (`lookup_cache`: real answers only, empty ones expire after 24 h); a `[identify]` log line gives the timings.
- **Receipt pages (Dev 1, done):** `/receipts/new` (photo downsized in the browser), then `/receipts/[id]` — the single screen after the scan: one card per product (photo of the 1st candidate, 200 px; known labels are pre-filled by the server so the photo is there on first render, the others are identified on load 3 at a time; name, price) with a "Ce produit a-t-il un problème ? Non (red by default) / Oui (green → issue presets)" toggle, "Ce n'est pas le bon produit", product choice, "je ne trouve pas mon produit", honesty checkbox. The old text-list screen and `/select` were merged into it. **`POST /api/claims` now returns `400 product_not_confirmed`** for any item whose `confirmed_product` is null: code or tests that create claims from seed data must call `/confirm` first (or set `confirmed_product` to `{"status":"not_found"}`).
- **UI (shared, done):** light cream theme only (no dark mode), Revolut-like: animated `Aurora` background + `glass` cards (`components/ui/aurora.tsx`) on every app page and login (not `/notcoca`). Design system in `components/ui` + tokens in `app/globals.css` (Plus Jakarta Sans + JetBrains Mono). ## Stack
Next.js (App Router) + TypeScript (strict) · Supabase (Postgres, Auth, Storage) · Vercel · H Company Agents API (`hai-agents` TS SDK) · Gmail (SMTP + IMAP, one dedicated account, per-claim plus addresses) · Stripe (test mode: Connect + Billing) · Linkup (unknown-brand lookup) · one LLM provider behind `lib/shared/llm.ts`: the H Models API (OpenAI-compatible, `LLM_URL` / `LLM_MODEL` / `LLM_API_KEY`, default `holo4-35b-a3b`). Change the model in the env, never in code. Thinking is turned off with `chat_template_kwargs.enable_thinking=false` (`holo4-35b-a3b` ignores `reasoning_effort`).

## Non-negotiable rules
1. **Honest claims only.** The complaint text may only contain facts the user provided (product, issue, description, receipt data). Never invent defects, quantities, dates or details. The agent prompt must forbid making up any field.
2. **Contracts first.** Changing the DB schema, `lib/shared/types.ts` or an endpoint shape means updating `API_CONTRACTS.md` in the same commit, plus a heads-up to the other dev.
3. **Ownership.** Stay inside your folders (see TEAM.md). Shared files (`lib/shared/**`, `supabase/migrations/**`, `package.json`) get small, single-purpose commits.
4. **Only Dev 2's code changes `claims.status` after `draft`.** Use `lib/claims/transition.ts`; never update the status directly.
5. **`AGENT_DRY_RUN=true` by default (also in production).** The agent stops before the final submit on every real brand. Only our fictional NotCoca site (`/notcoca` on `APP_URL`) is submitted for real. Set it to false only for a verified, genuine claim. Don't spam real brands.
6. **Don't invent external API behavior.** For H, Gmail, Stripe, Linkup, Gladia and the LLM, check the official docs before using an endpoint or field. If something is unverified, say so in a code comment.
7. No new infrastructure (queues, extra services, ORMs) without both devs agreeing. Supabase JS client + generated types only.
8. **Product identity comes only from `line_items.confirmed_product`** (API_CONTRACTS §2, §5). It is NULL until the user validates a product.
   - `status: "confirmed"`: use its `name`, `brand`, `ean` (mirrored in `product_name`, `brand_name_guess`, `ean`). Either a database product (EAN verified) or, with `source: "user"`, a product the user typed by hand: then `ean` is null and the name/brand are the user's own facts.
   - `status: "not_found"` or `null`: the claim goes out marked **"produit non identifié"**. Quote `raw_label` as printed; never state a brand or an EAN.
   - Before confirmation `product_name` is just `raw_label`. Never present `raw_label`, `product_candidates` or the LLM's `llm_guess` as the identified product.
9. **API calls cost credits** (H models, Linkup). No loops or batches of paid calls without asking. Linkup credit is shared by brand lookup and product search: never retry it automatically. Measure receipt-parser changes with `npm run eval:extract -- --cached` (no model call).

## Conventions
- Money is in integer cents (`*_cents`); dates are ISO strings; IDs are UUIDs.
- DB types are generated with `npx supabase gen types typescript` → `lib/shared/database.types.ts`. Never hand-edit that file.
- Server-only secrets never go in `NEXT_PUBLIC_*` env vars. Service-role Supabase client only in route handlers and server code.
- The UI targets phone width first (375px). The UI is in French. Light theme only: use `components/ui` and the `app/globals.css` tokens.
- Validate external input (webhooks, LLM output) with zod.
- Prefer server components + route handlers; client components only where interaction needs them.
- Vercel rejects request bodies over 4.5 MB: downsize photos in the browser before uploading them.

## Commands
- `npm run dev`: local app
- `npm run lint && npm run typecheck`: run before every push
- `npm run db:push`: apply migrations to the hackathon project (`--remote`; CLI v3 defaults to local Docker)
- `npm run seed`: seed brands + demo data
- `npm run db:types`: regenerate `lib/shared/database.types.ts` after a migration
- `npm run test:receipts`: receipt interpretation cases (no network, no model)
- `npm run eval:extract [-- --cached | --runs N | --only id1,id2]`: receipt extraction eval on `tickets/` (`--cached` = saved transcripts, no model call)
- `npm run spike -- <contact_url> [--brand X] [--product "…"] [--agent h/web-surfer-pro] [--receipt file.jpg]`: dry-run the H agent on a brand form (never submits)
- `npm run stripe:demo-account`: create the demo user's Stripe Connect test account + print a hosted onboarding link (single-use, expires in minutes)
